# Why the Self-Contained Stdio Server (v3.0.0) Was Abandoned

*July 5, 2026. Archive type: decision. Written two days after the revert, so the reason survives outside Kolja's head.*

v3.0.0 (shipped July 2, 2026) converted ES Memory into a self-contained stdio MCP server: Claude Desktop or Claude Code spawned the app directly from a `.mcpb`, with the engine in-process. It installed beautifully — the first external clean-machine install ("it just works," Marcus, July 3) validated exactly what it was built for: removing the launch-a-second-app failure surface. Two days later it was reverted (`c432e9b`, completed in `0f4915d`).

**The reason: stdio spawning breaks the single-writer property.** The MCP client owns the server process lifecycle under stdio transport — and every client session spawns its *own* process. Claude Desktop plus one Claude Code session equals two full in-process engines, each with its own Core Data stack, simultaneously open on the **same** persistent store (same bundle id, same container, same CloudKit-synced SQLite database). Nothing in the design serialized writes across those processes. The HTTP architecture never had this problem: one long-lived server process is the sole writer, all clients — any number of concurrent Claude sessions — reach it over localhost, and every database access funnels through a single dispatcher. Concretely, the dispatcher's serialization point is the **main queue**: MCPServer `dispatch_sync`s every tool call onto the main thread (`MCPServer.m`, `-dispatch…` path) after GCDWebServer's background queues receive it, so all operations — across every persona port and every simultaneous AI client — execute in strict order on one thread against a main-queue Core Data context. That mechanism is inherently per-process, which is exactly why stdio spawning defeated it: each spawned instance had its own perfectly serialized main thread, and nothing serialized *between* processes.

The failure is invisible in exactly the situation where the install experience shines: a single-session user never opens two instances. It appears the moment the author's own daily pattern — multiple concurrent sessions — meets the archive. That inversion (the demo case validates, the daily case corrupts) is why this document exists: any future "let's make it self-contained again" impulse must first answer *how N spawned processes share one store with one writer*. Options that were **not** pursued (and why a future attempt shouldn't assume they're easy): SQLite-level locking is not Core Data-level correctness; a spawn-time singleton handoff re-introduces the second process as a forwarder — which is just the bridge again with extra steps.

**Resulting architecture (current):** the engine lives only in **ES Memory MCP**, a localhost HTTP server (single target, v1.7, App Store/TestFlight distribution). Claude reaches it through the separate [ES-Memory-Bridge](https://github.com/apocryphx/ES-Memory-Bridge) — a thin stdio→HTTP forwarder `.mcpb` (v2.6.1) that is spawned per-session and is *safe* to spawn N times precisely because it holds no engine and no store. The `.mcpb` manifest slug stays `es-memory-bridge` so v3-era installs upgrade in place; note that anyone who installed the self-contained 3.0.0 `.mcpb` (e.g. Marcus) must install the server app when they upgrade, or their memory tools go dead.

The EmbeddingGemma embedder, shipped inside the v3.1.0 label, survives the revert — the embedder change was orthogonal to the transport experiment.
